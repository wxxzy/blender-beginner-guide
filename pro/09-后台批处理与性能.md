# 09 · 后台批处理与性能

> 前面八章都在界面里点；这一章让 Blender **不需要界面也能跑**。
> 当你有一百个镜头、或者要跑一整夜的流体模拟，图形界面是负担。

---

## 它解决什么问题

**你不该守着屏幕等渲染。**

一次 4K 渲染 10 分钟，十个镜头就是两小时。这段时间你本可以继续建模。
更别说流体模拟——80 帧可能要跑五分钟，中途改个参数又得重来。

后台模式让你：

- 把整套流程写成脚本，一条命令跑完
- 挂到服务器上无人值守
- 批量处理 100 个 `.blend` 文件
- 在 CI 里做"每次提交自动出预览图"

---

## 核心概念

### 三个命令行参数

```bash
blender -b model.blend -P script.py -- arg1 arg2
```

| 参数 | 作用 |
|---|---|
| `-b` | 后台模式，不开窗口 |
| `-P file.py` | 执行 Python 脚本 |
| `--` | 之后的内容原样传给脚本（Blender 自己不看） |

`--` 很重要：不写它，Blender 会尝试把 `arg1` 当成自己的参数解析并报错。

### 脚本里怎么拿参数

```python
import sys
argv = sys.argv
OUT = argv[argv.index("--") + 1] if "--" in argv else "./out"
```

### 三种"批量"层次

| 层次 | 做法 | 适合 |
|---|---|---|
| 单文件多帧 | `-a` 参数直接渲染整个动画 | 已做好动画的项目 |
| 单文件多设置 | 脚本里循环改参数再渲染 | 出多套方案对比 |
| 多文件批处理 | 外层脚本遍历 `.blend` | 项目集、素材库 |

## 可运行代码

### 基础模板：任何后台脚本的骨架

```python
"""通用后台脚本骨架"""
import bpy, os, sys, time

# ① 取参数
argv = sys.argv
args = argv[argv.index("--") + 1:] if "--" in argv else []
OUT = args[0] if args else os.path.join(os.path.dirname(bpy.data.filepath), "out")
os.makedirs(OUT, exist_ok=True)

t0 = time.time()

# ② 配置
sc = bpy.context.scene
sc.render.engine = "BLENDER_EEVEE"
sc.render.resolution_x = 1600
sc.render.resolution_y = 900
sc.render.image_settings.file_format = "PNG"
sc.eevee.taa_render_samples = 56

# ③ 干活
for frame in (1, 60, 120):
    sc.frame_set(frame)
    sc.render.filepath = os.path.join(OUT, f"frame_{frame:04d}.png")
    bpy.ops.render.render(write_still=True)
    print(f"[{time.time() - t0:6.1f}s] 完成 frame {frame}")

# ④ 保存工程
bpy.ops.wm.save_as_mainfile(filepath=os.path.join(OUT, "result.blend"))
print("全部完成，总耗时 %.1fs" % (time.time() - t0))
```

运行：

```bash
blender -b scene.blend -noaudio -P render_batch.py -- ./out
```

`-noaudio` 建议加上：后台模式没有音频设备，某些系统会卡一下。

### 批处理多个文件

外层用 shell 或 Python 遍历：

```bash
for f in ./projects/*.blend; do
  echo "=== $f ==="
  blender -b "$f" -noaudio -P render_batch.py -- "./out/$(basename "$f" .blend)"
done
```

在 Python 里更可控（能捕获退出码、写日志）：

```python
import subprocess, pathlib, sys

BLENDER = r"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe"
SCRIPT = "render_batch.py"

for blend in pathlib.Path("./projects").glob("*.blend"):
    out = f"./out/{blend.stem}"
    cmd = [BLENDER, "-b", str(blend), "-noaudio", "-P", SCRIPT, "--", out]
    r = subprocess.run(cmd, capture_output=True, text=True)
    ok = "RENDER_OK" in r.stdout or r.returncode == 0
    print(f"{blend.name}: {'成功' if ok else '失败'} ({r.returncode})")
    if not ok:
        print(r.stderr[-800:])
```

### 直接渲染动画

已经做好动画的项目，不需要写脚本：

```bash
blender -b scene.blend -noaudio -a
```

输出到 `scene.render.filepath` 指定的位置，帧范围由场景的 `frame_start/frame_end` 决定。

## 实测数据

这台机器（**无独显**，Intel Ultra 5 235U / 15.5 GB RAM / 14 线程）的真实耗时：

| 任务 | 设置 | 耗时 |
|---|---|---|
| EEVEE 单帧 | 1600×900 / 56 采样 | 25–30 s |
| EEVEE 单帧 | 2400×1350 / 96 采样 | 约 40 s |
| EEVEE 单帧（体积光） | 1000×660 / 64 采样 | 35–45 s |
| Cycles CPU 烘焙 | 1024×1024 / 6 采样 | 约 15 s |
| MPM 流体求解 | 96 分辨率 / 80 帧 | 约 60 s |
| 刚体模拟 | 14 物体 / 90 帧 / 12 子步 | 约 8 s |
| 布料模拟 | 1681 顶点 / 90 帧 | 约 12 s |
| 毛发渲染 | 6000 母发 × 6 子发 | 约 30 s |

**关键结论：这台机器上 Cycles 不划算。** 同样的画面，Cycles CPU 要 5–10 分钟，
EEVEE 只要 30 秒。除非必须用 Cycles 的特性（真实折射、复杂 GI、烘焙），否则一律 EEVEE。

有独显的机器结论会反过来——Cycles GPU 在 30 秒内能出 EEVEE 质量更高的图。

## 性能调优：按影响排序

### 1. 分辨率（最有效）

像素数翻倍 = 耗时约翻倍甚至更多。1600×900 → 3200×1800 是 4 倍像素。

**做法：先用 800×450 调构图，定稿再上最终分辨率。**

### 2. 采样数

EEVEE 的 `taa_render_samples`：

- 32：预览够用，噪点明显
- 56：常规出图
- 96+：有体积、透明、毛发时

体积散射和毛发最吃采样。这两样出现时，采样别低于 64。

### 3. 体积与流体分辨率

- 流体的 `resolution_max` 是**立方级**开销：96 → 160 大约 4 倍时间
- 体积的 `volumetric_samples` 同理

**先降到 48/64 看形态，确定后再提。**

### 4. 场景复杂度

- 毛发粒子：子发数量是主要成本（`rendered_child_count`）
- 高模：超过 500 万面后，EEVEE 的阴影计算明显变慢
- 透明材质：每层透明都要重算，叠 5 层就慢

### 5. 复用而不是重算

物理与仿真都有缓存。第二次渲染同一段动画时，**不要重建场景**：

```bash
# 第一次：建场景 + 烘焙物理
blender -b --factory-startup -P build.py

# 之后：直接打开已烘焙的 .blend 渲染
blender -b built.blend -a
```

我最初每次都从 `--factory-startup` 重建，导致流体每次都重算 60 秒——
存成 `.blend` 后，缓存一起被保存，第二次是秒开。

## 实测踩坑

### ① 不加 `--`，参数会被 Blender 吃掉

```bash
blender -b -P s.py ./out            # ❌ Blender 试图解析 ./out
blender -b -P s.py -- ./out         # ✅
```

表现是脚本里 `sys.argv` 拿不到你以为的东西，或者 Blender 直接报"unknown argument"。

### ② `bpy.context` 在后台模式是"残缺"的

界面相关的对象都不存在：

```python
bpy.context.area          # None
bpy.context.region        # None
bpy.ops.view3d.*          # 会报 context incorrect
```

所以后台脚本里**不能用依赖界面的操作符**：

- `bpy.ops.object.mode_set` 通常可用（只要 active object 对）
- `bpy.ops.uv.smart_project` 可用（在编辑模式内）
- `bpy.ops.view3d.view_selected` 不可用
- 截图类操作全部不可用

### ③ 需要"界面"的操作要用 override

少数操作符可以靠 context override 跑起来：

```python
with bpy.context.temp_override(area=area):
    bpy.ops.some.op()
```

但后台根本没有 area，所以这条路通常走不通。**换 API 而不是硬凑 context。**

### ④ 退出码不一定反映成败

Blender 在脚本抛异常时**有时仍返回 0**（尤其异常被 `try` 吃掉时）。
判断成功要靠日志标记：

```python
print("RENDER_OK", name)      # 脚本里埋标记
# 外层判断 "RENDER_OK" in stdout
```

我在验证脚本里每个功能都打一行 `RENDER_OK`，就是为了外层能可靠判断。

### ⑤ 保存路径别用相对路径

```python
sc.render.filepath = "//out/frame.png"     # 相对于 .blend
sc.render.filepath = "./out/frame.png"     # 相对于"进程当前目录"——容易错
```

后台模式下当前目录可能和你以为的不一样。**统一用绝对路径，或者 `//` 前缀。**

### ⑥ 物理缓存要跟着 .blend 存

如果缓存是"磁盘缓存"（`cache_type = 'DISK'`），路径要设成 `//cache/`，
否则换机器就丢。内存缓存（默认）会随 `.blend` 保存，但文件会变大。

### ⑦ 长时间任务要打印进度

一次跑 3 小时，如果中途崩了，你希望知道崩在第几帧：

```python
for i, frame in enumerate(frames):
    sc.frame_set(frame)
    bpy.ops.render.render(write_still=True)
    print(f"[{i+1}/{len(frames)}] frame {frame} OK", flush=True)
```

`flush=True` 很重要——否则输出会缓冲到最后一起打印，等于没打。

## 一个完整的生产脚本

把上面所有东西合起来，一个能挂夜跑的脚本长这样：

```python
"""夜间批渲染：多分辨率 + 多帧 + 断点续跑"""
import bpy, os, sys, time

argv = sys.argv
OUT = argv[argv.index("--") + 1] if "--" in argv else "./out"
os.makedirs(OUT, exist_ok=True)

sc = bpy.context.scene
sc.render.engine = "BLENDER_EEVEE"
sc.render.image_settings.file_format = "PNG"

JOBS = [
    ("preview", 800, 450, 24, [30, 90, 150]),
    ("final", 2400, 1350, 96, [30, 90, 150]),
]

t0 = time.time()
for tag, w, h, samples, frames in JOBS:
    sc.render.resolution_x, sc.render.resolution_y = w, h
    sc.eevee.taa_render_samples = samples
    for f in frames:
        path = os.path.join(OUT, f"{tag}_{f:04d}.png")
        if os.path.exists(path):
            print(f"跳过已存在 {path}")
            continue
        sc.frame_set(f)
        sc.render.filepath = path
        bpy.ops.render.render(write_still=True)
        print(f"[{time.time()-t0:7.1f}s] {tag} frame {f} OK", flush=True)

print("ALL_DONE")
```

这段脚本有三个实用设计：

1. **两级质量**：先出小图确认，再出大图
2. **断点续跑**：`os.path.exists` 跳过已渲染的帧，崩了重跑不重复劳动
3. **统一时间戳**：每行都带累计耗时，方便估算总时长

---

## 本章要点

- `-b` 后台 + `-P` 脚本 + `--` 传参，是批处理的三件套
- 后台没有 area/region，依赖界面的操作符用不了
- 成功判断靠日志标记，不能只信退出码
- 分辨率是最有效的性能杠杆，先小图后大图
- 物理/流体缓存要随 `.blend` 存，避免重复计算
- 长时间任务：打印进度 + 断点续跑

## 结语

九章下来，你摸过的东西已经覆盖了 Blender 的绝大部分"专业模块"：

雕刻与重拓扑、刚体与布料、流体与毛发、骨骼与 IK、UV 与烘焙、
体积光与色彩管理、资产库与插件、几何节点循环、后台批处理。

它们的共同点不是"难"，而是**参数多、默认值不友好、报错信息含糊**。
真正省时间的做法不是背参数，而是：

1. 先用低精度跑通流程（分辨率 48、迭代 3 次、采样 16）
2. 确认形态对了再提精度
3. 每个参数只改一个，看结果变化
4. 把踩过的坑写下来——下一次能省一小时

这份教程的"实测踩坑"部分，就是按第 4 条积累出来的。
